# Пользовательские AI-ассистенты на базе Hermes Agent

Актуальность: 18 августа 2026 года. Ниже сначала рассмотрены реальные решения вокруг NousResearch Hermes Agent. Общерыночные аналоги приведены только в приложении и не являются архитектурным ориентиром.

## Короткий вывод

Charline должна остаться тонким пользовательским слоем над одним Hermes Gateway. Лучшие Hermes-решения сходятся в четырёх принципах:

1. разговор остаётся главным интерфейсом;
2. ассистент сначала показывает то, что требует внимания, а не каталог возможностей;
3. кнопки появляются рядом с конкретным решением или объектом;
4. техническое управление отделено от ежедневного пользовательского интерфейса.

Мы заимствуем эти принципы, но не переносим отдельные Telegram-поллеры, базы памяти, планировщики, worker-plane и web-панели. Они дублируют уже существующие механизмы Hermes и нарушают архитектурные инварианты Charline.

## Что заимствуем

### 1. Attention-first вместо dashboard-first

Из Alfred и GBrain берём правило: первый экран отвечает не «что умеет система», а «что сейчас требует моего решения». Дневной ответ Charline должен располагать данные так:

1. конфликты, просроченные обязательства и недоступные источники;
2. ближайшие важные события и письма;
3. не более трёх второстепенных элементов на источник;
4. время проверки и source handles.

Сырые коды ошибок, tool traces и длинные результаты поиска пользователю не показываются.

### 2. Разговор как основной интерфейс

Главная карточка не является каталогом инструментов. Постоянное Telegram-меню содержит пять пользовательских состояний: `Сегодня`, `Проекты`, `Задачи`, `Расписания`, `Настройки`. Это не переименованные технические экраны: `Сегодня` запускает живой модельный синтез, `Задачи` содержит личные дела владельца, а процессы агентов остаются частью проекта и технической диагностики.

### 3. Проект как устойчивый контекст

Нативная Telegram topic остаётся границей project session. Исходный запрос переносится в неё полностью и сразу запускается обычным Hermes agent turn. Для работы, которая должна пережить рестарт, используются нативные Kanban tasks, dependencies, handoffs, review и точная подписка topic. Отдельный Google-документ не обязателен и не является project database; артефактом может быть репозиторий, файл, документ, сайт или несколько из них.

### 4. Кнопка обозначает конкретный результат

Inline-кнопки нужны только для ограниченного выбора или действия над видимым объектом:

- `Подтвердить` / `Отмена` для внешней записи;
- `Остановить работу` для конкретного процесса;
- `Пауза`, `Продолжить`, `Удалить` для конкретного расписания;
- варианты короткого уточняющего вопроса.

После действия клавиатура удаляется или карточка обновляется. Абстрактные кнопки `Управление`, `Подробнее`, `Сводка`, `Как создать…` не нужны.

### 5. Явная, управляемая пользователем автономность

V1 работает на уровне Confirming: чтение и анализ выполняются сразу, внешняя запись всегда требует точного preview и подтверждения. Если позже появится Acting, повысить уровень сможет только пользователь, отдельно для узкого класса действий; неизвестная политика должна завершаться отказом, а автоматическое действие — оставлять проверяемый след.

### 6. Полезная тишина

Из Life OS берём не его runtime, а пользовательское правило: плановый запуск не обязан отправлять сообщение, если нет нового полезного сигнала и пользователь выбрал тихий режим. Состояние Gateway, стоимость токенов и успех внутреннего cron сами по себе не являются пользовательской новостью.

## Что убираем и не добавляем

| Было или предлагалось | Решение |
|---|---|
| `Задачи`, показывавшие background/delegation Hermes | Исправлено по смыслу: теперь это личные дела владельца; процессы не подменяют задачи. |
| `Расписания` | Сохранено как понятное имя нативных Hermes cron jobs: напоминаний, сводок и плановых запусков. |
| `Сегодня`, показывавшее процессы Hermes вместо данных дня | Исправлено: команда запускает обычный Hermes turn, который читает актуальные источники и синтезирует день. |
| `Системные команды` в настройках | Убраны. Полный технический каталог остаётся в ручном `/commands`. |
| Пустой topic, после которого пользователь повторяет исходную задачу | Убрано: содержательный запрос передаётся в topic целиком и запускается там сразу. |
| `Как создать проект/расписание` | Убрано. Empty state показывает одну готовую естественную фразу. |
| Постоянные кнопки Mail, Calendar, Files, Research, Memory | Убраны с Home. Это намерения разговора, а не разделы ежедневной навигации. |
| Отдельный poller/router/session store/scheduler/memory DB | Не добавляются. Всё это уже принадлежит Hermes или Google Workspace. |
| Tool progress, raw traces, costs, model/provider/plugin controls | Остаются operator-level данными и не попадают в пользовательский Telegram UI. |

## Целевая пользовательская история

```text
Пользователь: Что важно сегодня?

Charline:
Требует внимания
• Конфликт: Созвон с Анной ↔ Демо [e1, e2]
• Просрочено: оплатить счёт [r1]
• Не удалось проверить: Почта

Дальше
• 12:30 — Обед с Ильёй [e3]

Проверено: 09:00 · Europe/Moscow
```

Пользователь получает синтез и понимает ограничения данных. Если он просит изменить событие, Charline показывает точную интерпретацию с часовым поясом, затем только `Подтвердить` и `Отмена`, выполняет одну запись и проверяет результат чтением API.

## Архитектурное решение

```text
Telegram text / voice / native topic
                 ↓
Hermes Gateway — polling, model loop, sessions, approvals, cron, delegation, Kanban
                 ↓
Charline plugin — тонкие детерминированные read models и карточки
        ├── dm_topics → Проекты
        ├── Hermes Memory → личные задачи и стабильные данные
        ├── Hermes cron → Расписания
        ├── Hermes Kanban → долговременная работа проекта
        └── domain skills → Google Workspace
```

Никакая из заимствованных идей не требует нового runtime. Google Workspace остаётся источником истины; внешняя запись проходит `preview → confirmation → one write → API read-back`; фоновый результат доставляется только в точный исходный chat/topic и не должен молча падать в Main.

## Приложение: общерыночная проверка

[ChatGPT Projects и Tasks](https://help.openai.com/en/articles/10169521-projects-in-chatgpt), [Gemini Connected Apps](https://support.google.com/gemini/answer/14959807), [Lindy](https://docs.lindy.ai/start-here/quickstart), [Notion Agent](https://www.notion.com/help/notion-agent) и [Khoj](https://github.com/khoj-ai/khoj) подтверждают те же верхнеуровневые паттерны: chat-first, ограниченный проектный контекст, естественное создание автоматизаций, отдельное управление подключениями и подтверждение внешних действий. Они использованы только как контрольная группа; решения выше приняты на основе архитектуры и пользовательских историй Hermes-экосистемы.
